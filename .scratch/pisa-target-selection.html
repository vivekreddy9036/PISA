Target selection & exploitation validation — research report, no repo changes

Pick the boring target. The XiongMai/DVR family beats every "cooler" RouterSploit module because it's the only one that doesn't hang PISA's own exploit adapter.

Grounded in the actual RouterSploit 3.4.7 source installed in this repo's venv (not memory), PISA's own M1/M2/M4 code, and follow-up market/prevalence research. Anything not independently confirmed is marked UNVERIFIED or UNCERTAIN — treat those as "go verify before you commit," not as facts.

TL;DR

Use two separate targets, not one target for everything — the brief's own §8 instinct is correct. Track A (assessment-only) should be OWASP IoTGoat, run on a separate host, not the Pi. Track B (real exploitation) should be a cheap, generic OEM DVR/camera device — not a "cooler" router RCE — because of one decisive, code-verified fact: 53 of RouterSploit's modules call an interactive shell() function that blocks on input() in an infinite loop, and PISA's M4 adapter (pisa/m4/routersploit_gate.py) has no code path that can drive that loop — calling run() on any of those modules today will hang the request thread indefinitely, not fail cleanly. That eliminates the "exciting" candidates (Netgear DGN2200 shell RCE, D-Link DIR-655 RCE, the P2P wificam RCE). Within the remaining safe candidates, follow-up research found a materially stronger evidence base for CVE-2018-9995 (generic DVR credential disclosure) than for the Xiongmai path-traversal candidate — a December 2024 FBI/CISA IC3 advisory (HiatusRAT campaign) and ~55,000+ still-indexed-vulnerable devices on Shodan as of 2024-2025, with no vendor patch existing for the TBK-derived clone family. That promotes it to primary.

1 Executive verdict

Safest path: OWASP IoTGoat for Track A, run on a laptop/small x86_64 host on the lab LAN rather than the Pi itself (see §6 — IoTGoat's official images target x86_64 hosts and Raspberry Pi 2, not Pi 4/aarch64) — structured identity → CPE → CVE → applicability → safe verification, no RouterSploit dependency. For Track B: a generic OEM DVR/NVR (TBK-clone family, CVE-2018-9995) as primary, a Xiongmai-firmware camera/DVR (CVE-2017-7577) as backup — both real, unauthenticated, non-destructive compromises via RouterSploit modules whose run() never calls shell(). Do not attempt the Netgear/D-Link/generic-camera RCE modules as the primary demo target — they are real, well-documented CVEs with working RouterSploit modules, but every one with a MIPS/reverse-shell payload in this codebase's module set drives PISA's adapter into a code path it cannot execute non-interactively today. That's a finding about PISA, not about the CVEs.

Decisive, code-verified

shell() will hang PISA's adapter. routersploit/core/exploit/shell.py:48 — while True: ... cmd = input(cmd_str). This is RouterSploit's own interactive console loop, meant to run inside rsf.py with a real terminal attached. grep -rl "shell(" modules/exploits against the installed 3.4.7 package returns 53 matching files. Any of those modules' run() called through PISA's _capture_output will block on input() forever — no attached TTY will ever satisfy it — freezing that Flask worker. This is not a hypothetical; it's the literal control flow of the confirmed candidate RCE modules (Netgear DGN2200, D-Link DIR-655/866/652, the P2P wificam RCE all call shell()).

Also found

RouterSploit's own check() can return three states, not two — True, False, or None ("could not verify"; e.g. routers/multi/misfortune_cookie.py returns None when the RomPager banner matches but the follow-up probe is inconclusive). PISA's adapter does bool(success), silently collapsing "could not verify" into "not vulnerable" — a real instance of exactly the missing middle state the architecture review flagged.

Why this is primary, not the Xiongmai candidate

Both are architecturally identical in risk profile (single HTTP call, no shell(), cheap hardware). This one wins on evidence recency and strength: a December 2024 FBI/CISA IC3 advisory ties this exact device family to the active HiatusRAT campaign, ~55,000+ devices remain indexed as vulnerable on Shodan as of 2024-2025, and the advisory states plainly that no vendor patch exists for TBK devices and their rebranded clones — this is about as strong a "still vulnerable today" signal as a 2018 CVE can have. It's also a stronger proof of compromise: it returns live admin credentials, not just a system file.

End-to-end validation steps

  1. Acquire: buy a cheap generic/rebrand 4-channel DVR kit (~$50-150) from a listing that does not emphasize a name-brand app/cloud ecosystem (Night Owl/Q-See branded units, ~$130-430, more likely run updated vendor firmware) — generic AliExpress/eBay "TBK-style" or "XVR 5-in-1" listings are the better bet per the prevalence evidence above. Still a gamble, not a guarantee — see §11.
  2. Isolate: dedicated lab VLAN/SSID with no route to production networks or the internet, PISA and target only.
  3. Network placement: connect the device to the same WiFi/LAN segment PISA's JOIN_IFACE joins for M1.
  4. Discover: M1 ARP sweep + Nmap finds the device, port 80 open.
  5. Identify: M2 HTTP probe fetches /, captures the Server header and any DVR/NVR keyword match — feeds today's keyword table ("nvr" already maps to "Network Video Recorder" in m2/http_probe.py) with zero new code required.
  6. CPE: attempt NVD CPE lookup for the identified product — expect empty/low-confidence (this OEM family plausibly has no clean CPE dictionary entry); the applicability engine must record this as its own state, not silently fail.
  7. CVE: a targeted lookup surfaces CVE-2018-9995 directly.
  8. Applicability: with no version data to confirm against, correct behavior is POTENTIALLY_AFFECTED, not AFFECTED — a good demonstration that the engine doesn't rubber-stamp everything.
  9. Verify: find_modules_for_cve("CVE-2018-9995") returns the module; check() confirms via the JSON credential response → VERIFIED_VULNERABLE.
  10. Locate module: already covered by step 9 — same call.
  11. check(): as above.
  12. run(): same request, returns the full username/password/role table.
  13. Proof of compromise: the extracted admin username and password — verify by logging into the device's own admin UI with the extracted credentials, which is the clearest, most unambiguous proof available: it demonstrates the credentials are real and functional, not just present in an HTTP response.
  14. Evidence: full HTTP request/response, the extracted credential table, confirmation-login result, timestamp, module path, operator — persist all of it, not just a text blob.
  15. Reset/recovery: none needed — read-only credential disclosure; no target-side state change occurs.

Confirmed: don't try to run this on the Pi

Checked directly against the OWASP/IoTGoat repo and wiki: IoTGoat ships an x86 .vmdk (VirtualBox/VMware) and a IoTGoat-rpi-2.img — that image targets Raspberry Pi 2 (32-bit ARMv7), not Pi 4 (64-bit ARMv8); direct-flash compatibility on a Pi 4 is unverified and not something to bet a deadline on. The documented QEMU-based emulation workflow (via the Firmware Analysis Toolkit) is tested only on Windows 10, Ubuntu 18.04, and macOS Mojave — x86/x86_64 hosts — with no ARM64 host testing anywhere in the docs. Practical conclusion: run IoTGoat on a laptop or small x86_64 server on the same lab network, not on the Pi. This doesn't weaken the demo — PISA is a network-based assessment tool and isn't expected to co-host its targets — but "PISA entirely self-contained on one Pi" isn't true for this target, and that should be stated plainly to the professor rather than glossed over.

Use this target for DISCOVER → IDENTIFY → CPE → CVE → APPLICABILITY → VERIFY only. Do not force it into the exploitation leg — RouterSploit has no IoTGoat-specific module, and hand-rolling an exploit for CVE-2020-28951 (a memory-corruption UAF) is exactly the kind of "sophisticated but hard to reproduce reliably" work the brief explicitly said to avoid. A safe verification check (e.g. confirming the vulnerable libuci-linked service is present/reachable, or exercising one of the deliberately-planted OWASP-Top-10 flaws such as a default-credential web login) is enough to reach VERIFIED_VULNERABLE without needing memory-corruption exploitation.

7 Negative control

Ground truth needed: a real, currently-sold, patched device that should correctly resolve to NOT_APPLICABLE or NOT_VULNERABLE — proving the applicability engine rejects as often as it confirms.

Recommended

TP-Link Archer AX21 (AX1800, WiFi 6) — confirmed still receiving active vendor firmware updates as of 2025 (community firmware release posts show monthly 2025 updates), sold new for roughly $70-100, and structurally unrelated to any of RouterSploit's CVE-tagged modules (all 25 target hardware/firmware from 2008-2019; this is a current WiFi-6 product line). Ground truth: no RouterSploit module should match any CVE surfaced for it, and a CPE lookup — if one succeeds — should show either no CVEs or only CVEs whose version ranges exclude the running firmware. Caveat: the assumption that zero RouterSploit modules target this specific model was not independently re-verified module-by-module in this pass — treat as reasonable but UNVERIFIED, and confirm with a direct find_modules_for_cve-style search against its actual CVE list before the demo.

8 Full end-to-end demo

Track A — OWASP IoTGoat (hosted on a laptop/x86_64 box on the lab LAN, not the Pi) DISCOVER (M1 ARP+Nmap finds IoTGoat's IP/ports) → IDENTIFY (M2 HTTP probe: OpenWrt/LuCI banner or admin page) → CPE (new: NVD CPE lookup for OpenWrt 18.06.2 family) → CVE (NVD CPE-match, not keywordSearch — surfaces CVE-2020-28951 + others) → APPLICABILITY (new: version range confirms AFFECTED) → VERIFY (new: safe check — default-cred login or service-presence probe → VERIFIED_VULNERABLE) → EVIDENCE (HTTP request/response, timestamp) → REPORT Track B — generic OEM DVR (TBK-clone family) DISCOVER (M1 finds device, port 80 open) → IDENTIFY (M2 HTTP probe: Server header + "nvr"/"dvr" keyword match) → CPE (likely empty — recorded as its own state, not NOT_APPLICABLE) → CVE (CVE-2018-9995, found directly) → APPLICABILITY (POTENTIALLY_AFFECTED — no version data to confirm further) → VERIFY (RouterSploit check() → VERIFIED_VULNERABLE) → FIND EXPLOIT (find_modules_for_cve — same module, already matched) → AUTHORIZED EXPLOIT (operator confirms, run() executes — real M4 code, unmodified) → COMPROMISE PROOF (extracted admin credentials, confirmed by logging into the device's own admin UI) → EVIDENCE (full request/response, extracted credentials, login confirmation, module path, timestamp, operator) → REPORT

9 Required PISA changes

Scoped strictly to what's needed to make §8 work — not the full architecture rework from the prior review.

  • Applicability/CPE layer (already identified as the core gap) — needed for Track A's CPE/applicability steps.
  • Verification state field on device_cves — needed so "VERIFIED_VULNERABLE" is a stored fact, not an inference from exploit_results.
  • check() three-state fix — m4/routersploit_gate.py's run_exploit must distinguish None ("could not verify") from False ("confirmed not vulnerable") instead of collapsing both via bool(). Small, precise fix.
  • Timeout on run_exploit — even for shell()-free modules, add a hard timeout (thread with join-timeout, or subprocess isolation) before demo day; don't rely on picking safe modules alone as the only safeguard.
  • Do NOT attempt to make shell()-based modules work for this demo. That's a real engineering project (feeding scripted commands into an input() loop, or monkeypatching routersploit.core.exploit.shell) with its own risk of introducing new bugs days before a deadline. Out of scope here.
  • Structured evidence fields on exploit_results (or a new evidence table) — request/response pairs, not just the existing text blob — needed for §4/§6's evidence steps to be more than a printout.

Single biggest risk

Buying a "generic Xiongmai/OEM DVR" today and having it actually run the ~2017-era vulnerable firmware is a real gamble — current-production units may have been patched, or may run different OEM firmware entirely despite superficially similar branding/listings. Mitigation: buy 1-2 units early (this week, not the week before the demo), and immediately run check() against them by hand before committing to this as the headline target. If neither confirms vulnerable, fall back to the DVR-creds-disclosure family with a different purchase, or de-scope Track B to a check()-only "verification available but exploit not confirmed on this specific unit" demo — which is still an honest, defensible result given this report's own rule against promising exploits that haven't been evidence-tested.

12 Final recommendation

Build this first

1) Order 1-2 cheap generic-OEM-DVR devices today (prioritize CVE-2018-9995-style generic/rebrand listings over name-brand ones) and hand-test check() from both candidate modules against them before anything else — this de-risks the entire Track B plan on the earliest possible date. 2) Stand up OWASP IoTGoat on a laptop/x86_64 host on the lab LAN (confirmed not Pi-native) in parallel. 3) Order the TP-Link Archer AX21 negative control — trivial, do it now, it's not on any critical path. 4) Build the applicability/CPE layer and the verification-state field from the prior architecture review — both tracks need it. 5) Add the check() three-state fix and the run_exploit timeout — small, precise, high-value fixes to the existing M4 adapter.

Do NOT build yet

Any support for shell()-based RouterSploit modules (Netgear DGN2200, D-Link DIR-655, P2P wificam RCE) — genuinely interesting exploits, but wrong bet against a fixed deadline given a confirmed, deterministic incompatibility with PISA's own adapter. Also do not build: a generic multi-backend exploitation abstraction, a full OWASP ISTG test-case engine, or Modbus/behavioral-drift features raised in the prior review — none of those are load-bearing for this demo.
