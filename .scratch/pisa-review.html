Independent architecture & research review — Second senior engineer pass

PISA is a real, working v1 — the proposed 10-engine redesign is not a rewrite, it's a data-model fix wearing a new org chart

Read against the actual repository (M0–M5, live), the 20-paper literature set, and the current IoT-pentest / vuln-intel ecosystem. Every claim below is anchored to a file, a line, or a named external source — not to the aspirational document.

TL;DR

PISA v1 is further along than the brief assumes: WiFi capture, network join, protocol fingerprinting, NVD/EPSS/KEV correlation, and a real RouterSploit exploitation gate all exist and run against live hardware — this is not vaporware. But the vulnerability-intelligence layer has a specific, fixable defect that undermines the entire "verify before exploit" claim: there is no CPE, no version-range matching, and no applicability state — CVE correlation is a free-text keyword search against NVD, meaning every "CVE found" today is closer to POTENTIALLY_RELATED than AFFECTED. The 10-engine pipeline in the brief is the right shape, but most of its boxes already exist under M0–M5 names; the actual work is: (1) add a structured identity → CPE → applicability layer, (2) add a verification state machine between "CVE exists" and "exploit ran," (3) stop claiming research novelty the current evaluation can't support, and (4) cut scope that has no lab target to prove itself against.

A Executive verdict

The direction is technically sound with one correction: don't treat this as "redesign PISA from scratch into a 10-engine architecture." Treat it as "PISA already built 7 of the 11 engines under different names — finish the applicability/verification layer that's actually missing, and stop letting the documentation claim things the code doesn't do."

Three things are true simultaneously, and the review has to hold all three:

  • The engineering is genuinely good in places. The RouterSploit adapter (pisa/m4/routersploit_gate.py) reverse-engineers two real integration seams (module discovery via name-mangled __info__, output capture via RouterSploit's own printer-thread mechanism) that RouterSploit doesn't expose as a public API — that's the kind of unglamorous, correct systems work a redesign should preserve, not throw away chasing an adapter-pattern abstraction the brief speculates about (Section 12). One exploitation backend, done honestly, beats three adapters with two of them half-working.
  • The vulnerability-intelligence layer is the one part that is actually broken, in exactly the way the brief warned about: lookup_cves/lookup_device_cves in pisa/m0/oui_cve.py query NVD's keywordSearch with a vendor string or a simplified Nmap OS guess. There is no CPE anywhere in the codebase (verified by grep — zero hits outside a stale doc reference). This is the single highest-priority fix, not a nice-to-have.
  • The project documentation is running two different stories — docs/PISA_SRS.md is honest, dated, and self-correcting (it explicitly marks features Implemented/Planned/Removed with real dates). docs/FYP_PROJECT_DOCUMENTATION.md is a "Version 3.0" research-novelty pitch targeting IEEE Internet of Things Journal (IF 8.2) that describes Modbus fingerprinting, behavioral drift detection, and a multiplicative ExploitScore formula — none of which exist in code. Before any redesign work starts, these two documents need to agree, and the aspirational one needs to lose claims the evaluation can't back up. See §K.

C.1 Corrected architecture

Same pipeline shape, but the box that was missing is now explicit, and the box that was over-built in the brief is now sized to what an operator with one lab and one deadline can actually finish.

DISCOVER (M0/M1, existing) → IDENTIFY (M1/M2, reworked output: structured identity, not a label) → MAP TO CPE (new — Applicability Engine, MVP-critical) → CORRELATE CVE (M3, reworked: CPE-match API, not keywordSearch) → DETERMINE APPLICABILITY (new — version-range check, confidence-tagged) → VERIFY (new — safe protocol/config checks, one state machine) → EXPLOIT (M4, existing, keep as single RouterSploit backend) → EVIDENCE (widen exploit_results into structured evidence rows) → SCORE (M3 ExploitScore, existing, extend with applicability weight) → REPORT (M5 dashboard, existing; PDF export deferred to v2)

E One target, end to end

Example: an OWASP IoTGoat instance on the lab network. Confirmed via the live OWASP/IoTGoat repo: it's built on openwrt-18.06.2, runs via QEMU (or as a VMDK / Firmadyne / ARM-X emulation), and deliberately carries real, citable vulnerabilities from its OpenWrt base — e.g. CVE-2020-28951, a libuci use-after-free — alongside OWASP IoT Top 10-mapped "easter egg" flaws. This is a concrete, verifiable CVE to design the MVP walkthrough around, not a placeholder.

  1. Discover: M1 join + ARP/Nmap finds 192.168.1.50, open 22/80/1883, Nmap OS guess "Linux 3.x (embedded)".
  2. Identify (reworked): M2 HTTP probe pulls the admin page title/server header ("IoTGoat"/OpenWrt banner); MQTT probe confirms broker present, no auth. Fusion today would output device_type="IoT Gateway", confidence=0.8 — a label. Reworked, it must output {vendor: "OpenWrt", product: "IoTGoat", version: unknown, evidence: [http_header, mqtt_banner], confidence: 0.8}.
  3. Map to CPE (new): query NVD's CPE API for candidate CPEs matching product="IoTGoat"/OpenWrt version family; if version is unknown, carry a CPE wildcard forward with an explicit version_unknown=true flag rather than silently guessing one.
  4. Correlate CVE (reworked): NVD CVE API 2.0 cpeName parameter (not keywordSearch) returns CVEs whose configuration nodes reference that CPE, with version-range operators (versionStartIncluding/versionEndExcluding) intact.
  5. Determine applicability (new): compare the fused device's version info (if any) against each CVE's version range → AFFECTED, POTENTIALLY_AFFECTED (version unknown), or NOT_APPLICABLE.
  6. Verify (new): run a safe, protocol-specific check for the matched CVE class (e.g., attempt MQTT connect with no credentials; confirm HTTP endpoint reachable without auth) → VERIFIED_VULNERABLE or NOT_VERIFIED, independent of whether an exploit exists.
  7. Exploit (existing M4): find_modules_for_cve against RouterSploit's index; if a match exists and is authorized, check() then optionally run().
  8. Evidence (widened): persist the HTTP/MQTT request-response pair from step 6, the RouterSploit captured output from step 7, and a timestamp+tool-version stamp — not just a result string.
  9. Score: ExploitScore as today, now gated so a NOT_APPLICABLE CVE never reaches the dashboard as a "finding" at all.
  10. Report: dashboard renders the full chain per finding — this is already 90% there in m5/templates/session_detail.html.

F Real exploitation — what's achievable and what isn't

RouterSploit is a real but narrow backend, and the codebase already knows this — the docstring in m4/routersploit_gate.py states the exact number: only 24 of ~358 modules cite an explicit CVE ID. Independently re-verified against the live threat9/routersploit repo: 143 exploit modules, 171 creds modules, 4 scanners, 32 payload generators (~350 total, matching PISA's own count), of which 25 of 143 exploit modules mention a CVE string — same picture, confirmed from the outside. The project is not abandoned (last commit 2026-05-05, 93 open issues, actively pushed), but there is no structured CVE metadata field in any module — PISA's substring match against free-text references is the only option there is, not a workaround for something better that was skipped. Coverage skews router/CPE-vendor (D-Link, Netgear, TP-Link) plus a small cameras category — not broad IoT, no BLE/Zigbee/industrial protocols. Treat "no matching module" as the expected, common outcome, not a bug to engineer around.

For scope beyond RouterSploit: Metasploit's own IoT/embedded/ICS coverage is comparably thin, but its msfrpcd/msgrpc RPC API is a real, documented, language-agnostic programmatic backend (confirmed at docs.rapid7.com/metasploit/rpc-api) — a legitimate second backend if and when RouterSploit's coverage is demonstrably the bottleneck. Not now (see Kill List, §K) — but worth knowing the path exists rather than speculating about an adapter interface with no second implementation to justify it.

What this means concretely for a demo: pick lab targets where the CVE is, in fact, one of RouterSploit's ~24 CVE-tagged modules, or where a hand-written PISA-native check (safe MQTT/CoAP/HTTP probes, no RouterSploit needed) can reach VERIFIED_VULNERABLE without needing a full exploit at all. Verification and exploitation are separable claims — don't let the demo depend on both landing on the same CVE.

G Vulnerability intelligence — audit

Critical

No CPE, anywhere. _query_nvd uses keywordSearch against a vendor name or a stripped Nmap OS-guess string. NVD's own documentation is explicit that keywordSearch is a free-text match over CVE descriptions — it ANDs every token and has no concept of version, making it prone to both false positives (unrelated CVEs mentioning the vendor name) and false negatives (relevant CVEs that don't happen to use the exact search term). The code already knows part of this — _simplify_os_guess exists specifically because a literal version string zeroes out results — but the fix taken was to strip version info rather than switch to CPE, which removes the symptom and keeps the disease.

High

No caching / no local CVE store. Every "Check CVEs" click is a live synchronous NVD call in the Flask request thread. No backoff/retry on 403/429, no local database of previously-seen CVEs to fall back to when offline — directly conflicts with the "field deployment may lack internet access" framing already in the SRS's own constraints section.

High

KEV catalog is frozen at commit time. pisa/m3/kev_catalog.json is checked into git and only downloaded if absent — it will never refresh on a long-lived install, and there's no stored catalog date to warn a user it's stale. A data file has no business being version-controlled.

Correct, mostly

CVSS handling is right for the field's current reality. v3.1 → v3.0 → v2 fallback order matches NVD's own reporting (not every CVE has a v3.1 score). CVSS 3.1 remains the dominant version industry-wide; NVD only began publishing 4.0 alongside 3.1 for newly-published CVEs in early 2026 and has no plan to retroactively rescore the historical database — so treating 3.1 as primary (as the code does) is the correct call, not a gap to rush-fix.

EPSS & KEV mechanics — current as implemented, verified against live docs

  • EPSS: m3/epss_client.py hits https://api.first.org/data/v1/epss?cve=... correctly, batches CVE IDs into one request. Doesn't use the date parameter — confirmed available (historical scores back to 2021-04-14, daily updates ~13:30 UTC) — so a future "was this exploitable-looking a month ago" view is possible without a new data source, just an unused parameter. Fine to skip for MVP; add a caching layer before demo day so a flaky network doesn't blank out every score live.
  • KEV: correct source. Missing: catalog version/date storage, scheduled refresh, and any surfaced distinction between "not in KEV" and "we couldn't check KEV" (both currently render as kev_listed=0). Note also that CISA sometimes updates fields on existing KEV entries (e.g. knownRansomwareCampaignUse) without a visible changelog — a naive "diff for new entries only" refresh strategy would miss these; refresh should replace the full local set, not append.
  • NVD rate limits (confirmed current): 5 requests/30s unauthenticated, 50 requests/30s with an API key — config.NVD_API_KEY already supports the key path; worth adding a client-side throttle so a bulk "fingerprint whole network → check all CVEs" flow doesn't 429 mid-assessment.

Do not let PISA say "CVE found → device is vulnerable"

This exact failure mode is present today. A network or device's CVE list is currently rendered with no applicability caveat — a keyword match on "Cisco" returns the same CVE list regardless of whether the actual device is a 2009 switch or a 2024 access point. The fix is not cosmetic (a disclaimer label); it requires the CPE/applicability engine in §C.1 to exist before the UI can honestly distinguish a real finding from a keyword coincidence.

New, changes the plan

NVD's own enrichment coverage degraded in April 2026 — this is not a hypothetical caveat, it already happened. Confirmed via NIST's own announcement: NVD's CVE backlog (93.4% "Awaiting Analysis" by May 2024) led NIST to formally switch, on 2026-04-15/16, to a risk-based triage model — roughly 29,000 backlogged CVEs were reclassified "Not Scheduled," and going forward only CVEs already in CISA KEV or tied to EO-14028 "critical software" get full CPE/CVSS enrichment. Practical consequence for PISA: building the CPE-applicability engine against NVD alone will still silently miss or mis-map a large share of CVEs for ordinary IoT/embedded products that aren't KEV-listed. The applicability engine's data-source design needs to account for this from day one — either treat "no CPE data yet" as its own explicit state (not NOT_APPLICABLE), or supplement NVD with CNA-native sources (GitHub Security Advisories, vendor PSIRTs) for products NVD hasn't triaged. Sources: nist.gov/news-events (2026-04), helpnetsecurity.com (2026-04-16), vulncheck.com/blog/nvd-backlog-exploitation.

B/I Device identity — the real blocker

The brief asks for an "identity fusion model, not a single guessed string." pisa/m2/fusion.py already does confidence fusion correctly as an algorithm — group candidate labels, sum confidence per candidate capped at 1.0, return the max. The defect isn't the fusion math, it's the fusion output shape: a single string (device_type) plus one float (fingerprint_confidence). There's no structured record of which evidence produced that label, no separate confidence per identity dimension (vendor vs. model vs. firmware version), and critically no field that could ever hold a CPE even if one were computed.

Concrete fix (small, not a rewrite): change the fused output from (device_type, confidence) to (vendor, product, version_hint, device_type, confidence, evidence[]), and have every M2 probe contribute to whichever field it actually has evidence for instead of collapsing everything into one label. This is what makes the applicability engine buildable at all.

N Security of PISA itself

Good, keep

Exploit target IP is read server-side from the device's DB row, never taken from the client request — a real, load-bearing safety property that prevents the exploit endpoint from being redirected at an arbitrary IP by tampering with the request body.

High

The 5-second confirmation gate (NFR-7) is client-side JS only. A direct POST /api/devices/<id>/exploit with any string in authorized_by bypasses it entirely — the gate protects against an accidental UI click, not against programmatic misuse. Acceptable for the current threat model (trusted single operator, loopback-bound) but should be called out explicitly as a UI safeguard, not a security control, before it's relied on for anything beyond a solo-operator demo.

High

run_device_exploit calls routersploit_gate.run_exploit synchronously in the Flask request thread with no timeout. A hung RouterSploit module (dead TCP connection, blocking read) hangs that worker indefinitely — with Flask's dev server this can starve the whole dashboard.

Note

Audit log (exploit_results) is a plain SQLite table with no integrity protection — anyone with file access can edit past authorization records. Not urgent for a solo-operator field tool; becomes relevant the moment PISA is positioned as producing evidence for a client engagement.

H Research contribution — be honest about this now

One finding from this review's market research is worth stating plainly because it cuts in PISA's favor: a dedicated search for actively-maintained, portable/Pi-based tools that chain recon → CVE correlation → exploitation for IoT (the P4wnP1 family, Hak5 Pineapple/Pager, netool, Flipper Zero) turned up no comparable project — the field-hardware category is Wi-Fi-MITM-only (Pineapple/Pager) or RF/NFC-only (Flipper); the enterprise XIoT category (Nozomi/Claroty/Armis/Forescout/Defender for IoT) is uniformly detect-and-score, never exploit. That combination is a real, specific, defensible gap PISA can occupy — once the applicability/verification layer exists to make "verify → exploit" trustworthy rather than "keyword match → exploit."

The FYP documentation's "5-Part Novelty Claim" targets IEEE Internet of Things Journal (impact factor cited as 8.2). That is not a realistic venue for this project's current evaluation depth — IoT-J requires large-scale empirical evaluation (the very papers PISA cites as baselines, P07/P10, test on 15,000+ traffic flows / 28+ device types). PISA's actual differentiator is systems integration on constrained hardware, which is a legitimate contribution — just not one an IoT-J-caliber venue rewards on its own.

What can actually be claimed:

  • A working, non-ML, cross-protocol device fingerprinting fusion running on Raspberry Pi 4 — measurable via fingerprint accuracy against a labeled set of 10-15 real lab devices, and resource consumption (CPU/RAM/time) during a full assessment run. This is a legitimate, modest, workshop or student-conference-scale contribution.
  • An empirical demonstration that combining CVSS+EPSS+KEV changes CVE prioritization versus CVSS alone, on a real device set — measurable, falsifiable, small.
  • Not claimable yet: anything requiring the applicability engine (precision/recall of CVE matching) — the current keyword-search approach would score badly against ground truth, so this metric should not be attempted for publication until the CPE rework lands.

Recommendation: reposition the paper as a systems/tools contribution (a realistic target: a security-tools workshop, or a national/regional student research conference) rather than a top-tier IoT journal, and drop "first system to do X" framing for claims that are true only relative to the 20-paper reading list rather than the broader literature (e.g., IoT device-ID accuracy work well beyond these 20 papers exists and should be acknowledged, not implied away).

I/J MVP and roadmap

MVP — smallest version that proves the full chain once

  1. Add status enum to device_cves/network_cves (states from §F).
  2. Rework M2 fusion output to structured identity (vendor/product/version_hint) — small change, high leverage.
  3. Add an Applicability Engine: NVD CPE API lookup from structured identity, version-range check against CVE configuration nodes, writes AFFECTED/POTENTIALLY_AFFECTED/NOT_APPLICABLE.
  4. Add 3-5 hand-written safe verification checks (MQTT no-auth connect, CoAP resource enumeration, HTTP default-creds probe) producing VERIFIED_VULNERABLE/NOT_VERIFIED — independent of RouterSploit.
  5. Widen exploit_results into structured evidence (request/response pairs, not just a text blob).
  6. Demonstrate the full chain against 2-3 controlled targets: OWASP IoTGoat running CVE-2020-28951 or an IoT-Top-10-mapped flaw (applicability engine resolves to AFFECTED, verified via a safe check, no RouterSploit dependency needed), a real router/camera in a home lab with a RouterSploit-covered CVE (proves the exploitation leg), and one device that correctly resolves to NOT_APPLICABLE (proves the applicability engine isn't just a rubber stamp). If a second, non-emulated physical target is wanted, DVID (Damn Vulnerable IoT Device) is a real open-hardware option (ATmega328p board, UART/BLE/Wi-Fi, used in published training courses) — but it requires buying/flashing physical hardware, so only pull it in if IoTGoat + one real device isn't enough for the demo.

v1 (post-MVP)

  • Local CVE cache with offline fallback; KEV catalog refresh with stored provenance; CVSS 4.0 handling; execution timeout + async job queue for exploit runs; expand verification checks to ~10 OWASP-ISTG-aligned categories.

v2

  • PDF report generation; multi-device batch assessment prioritization; expand Modbus/BACnet probes if a real target justifies it (don't build speculatively).

Future (explicitly not now)

  • AWS cloud sync, GPS/touchscreen hardware integration, second exploitation backend (Metasploit RPC) — only once RouterSploit's coverage is demonstrably the bottleneck, not before.

K Kill list — and what's bullshit right now

Cut

Behavioral drift detection as a v1/v2 feature. It's schema-only today, described in the FYP doc as a differentiator ("converts PISA into a longitudinal monitoring platform"), and requires repeated-session baseline data this project has no time to collect and validate. Either implement it minimally and honestly, or remove the claim.

Cut / overclaim

Modbus fingerprinting — claimed in the novelty section, zero implementation. Either add one probe module (small, real work) or remove the claim from the FYP doc. Right now it's a sentence, not code.

Cut

Multi-backend exploitation adapter abstraction (RouterSploit / PISA PoC / Metasploit / custom, per the brief's §12). One working backend beats a speculative interface with three stub implementations. Build the abstraction when a second real backend exists, not before.

Cut

Generic Test Case Engine / OWASP ISTG interpreter. Automating the full ISTG is explicitly out of scope per the brief's own instructions (§14) — but the 10-engine pipeline as drawn implies a generic engine anyway. Build 5-10 hardcoded checks, not a framework for checks.

Downgrade claim

"IEEE IoT-J, IF 8.2" target. Not reachable with this evaluation scope. Reposition per §H before it's cited anywhere the review panel or a co-author will hold you to it.

Fix, don't cut

"CVE found" language in the dashboard/reports. This isn't a feature to remove — it's a phrase that must not ship again once the applicability engine exists. Every "CVE found" surface needs a status badge (POTENTIALLY_AFFECTED vs AFFECTED vs VERIFIED_VULNERABLE) before this is defensible in front of a review panel or a real client.
